# Review: V7 `space.upgrade` and the GE + FS + O split

- **Date:** 2026-10-20
- **Branch:** `docs-ge-fs-o`
- **Committed baseline:** `f3ff602` (V7: `cc637af`, `0da2bd5`, `916c340`)
- **Also reviewed:** the uncommitted GE + FS + O working-tree change
  (`sys/src/9/gefs/*`, `sys/src/9/port/devgefs.c`, docs and test scripts)
- **Method:** static code review. No code was changed and no test was
  re-run for this review; the test results quoted below are the ones the
  commits and existing logs claim.

## Verdict

The V7 core is substantial and the test suite is broad. The pin/K logic
matches the specification, publication is a single committed `c` record,
and the upgrade tests T7.1-T7.12 cover the main paths. Two V7 issues still
break stated invariants: persistent OIDs of methods in a changed class are
not preserved (I3), and the upgrade persists the caller process's
`__main__` globals into the Space. The GE + FS + O refactor propagates the
volume context carefully, but its shared cache-budget allocator makes a
second volume impossible, and the user-id constants are still global, so
the multi-volume isolation the change announces is not reachable yet.

## V7

### V7-1. Methods of a changed class lose their persistent OIDs

`upg_funs()` calls `bindfun()` for every `O_FUN` in the OID table, including
methods stored in class dictionaries (`p9image.c:2768`). `bindfun()` creates
a new function `nf` from the new module's raw code and moves the old OID to
it with `oidmove(f, nf)` (`p9image.c:2731`), so the replacement map contains
`f -> nf`.

`upg_classes()` then runs after the functions. `bindclass()` executes the
new class body and creates a **second** new function `nv` for each method.
`classmembers()` overrides the mapping with `rset(f, nv)` and calls
`oidmove(f, nv)` (`p9image.c:2809-2810`), but `f` has already been removed
from the OID table by the first move, so the second move is a no-op.

`remapdict()` then installs `nv` in the class dictionary
(`p9image.c:2935-2936`). The old OID stays on the now-unreachable `nf`.
At commit either an orphan record with the old OID is written and `nv`
receives a new OID, or, if the GC frees `nf` first, a tombstone for the old
OID is written. Either way `space.oid(C.m)` changes or disappears after an
upgrade whose module changed, which violates I3 ("Existing OIDs are
unchanged for surviving ... persistent named functions").

The tests do not catch this: they check the OIDs of instances, lists,
classes, and dictionaries, but not of methods (`tools/test-space.sh:863-898`).

Suggested direction: move the OID from `rget(f)` (that is, `nf`) to `nv`,
or leave class-dictionary functions out of `bindfun()` and let
`classmembers()` perform the move.

### V7-2. The upgrade commits the caller's `__main__` globals

`rootdict()` returns the live `MP_STATE_VM(dict_main)` as the restored
`__main__` (`p9image.c:1886`), and `fill()` adds entries to it without
clearing it first (`p9image.c:1758`). `space.upgrade` then restores and
commits that same process dictionary (`p9space.c:1517-1528`,
`1569-1575`).

Consequently, the upgrade process's own globals become part of the Space's
`__main__`. The documented invocation
`mp -c 'import space; space.upgrade(...)'` at least persists the `space`
module (as `V_BUILTIN`). A larger driver script persists all of its globals;
a non-persistable global (a lambda, an open file) makes the commit fail with
"not persistent", which makes the feature fragile to use from scripts.

The tests do not inspect `__main__` after the upgrade, so they do not see
this. The restore should use an isolated `__main__` dictionary (or clear
the process dictionary in a controlled way) before publishing.

### V7-3. "Ambiguous" names are not detected

`p9_image_symtab` marks only the **new** duplicate entry as `0xff`
(`p9image.c:2220`), and `symfind` returns the first matching name
(`p9image.c:2249`). With two module-level `def f` (or `class C`)
definitions, an upgrade silently binds to the first, shadowed definition,
although I4 requires an ambiguous name to abort. The scope-count check in
`p9_image_symcheck` still passes, so nothing else catches it.

Fix direction: mark all matching entries, or make `symfind` inspect every
matching entry and report ambiguity.

### V7-4. An alias can steal the identity and cause a false rejection

`scanmap`/`nadd` accept the first name encountered in the dictionary's hash
order (`p9image.c:294-315`, `206-230`, `nameof` at `371`). If a module
contains `def f` and `g = f`, the function's recorded identity can become
`g`. The new source's symbol table contains only `f`, so `newrcfun` rejects
the upgrade with "not in the new Environment" (`p9image.c:2568-2620`).

T7.2 stores its alias in `__main__`, not in the same module, so it does not
exercise this case. When naming an object, the implementation should prefer
a name that is a definition in the new symbol table, or retain all names
and try them.

### V7-5. New bases and module-level class decorators are silently ignored

`bindclass()` takes the bases from the **old** class
(`classbases(t, ...)`, `p9image.c:2900`) and executes only the class body's
raw code (`2917-2925`). A changed source such as `class C(NewBase):`, a
metaclass or other class keyword, and a decorator on a module-level class
(`@register class C`) are never evaluated. The upgrade succeeds but the
new definition's inheritance and decoration do not take effect. This should
either be implemented or rejected explicitly rather than silently ignored.

### V7-6. The epoch catalog is global and can leak on error

`epochs` is a file-scope array in `p9space.c`. `readcat()` returns 1 for
"no catalog" without clearing it (`p9space.c:814-830`), and the `envat`
failure paths in `space_open` (`1066-1069`) and `space_view`
(`1325-1328`) raise without calling `epochclear()`.

If user code catches such an exception and later opens a historical version
of a V5/V6 store (no catalog), stale epochs from the previous Space can be
consulted and the wrong Environment selected. Clearing at the start of
`readcat()` and in every error path would make this robust.

### V7-7. Smaller V7 issues

- `catparse` calls `get64(p + 5)` even when `n == CatHdr == 9`
  (`p9space.c:649`), reading five bytes past the buffer. The catalog is
  rejected afterwards, but the over-read is real.
- A failed upgrade leaves `sp.fmt` and `sp.pin` set (`p9space.c:1569-1570`,
  `1596-1598`). A subsequent V2-V4 open in the same process (the no-store
  branch of `space_open`) can inherit fmt 2 and the stale pin and write an
  88-byte header with a bogus pin.
- `scanmap` recurses into classes only to depth 2 (`p9image.c:330`).
  Named classes/functions below that are unnamed, so an upgrade of a
  changed module refuses them. That is an acceptable explicit failure, but
  the limit is not documented.
- `epochadd` loses the original allocation if `realloc` fails, and
  `p9_image_symtab` does not check the `path` allocation. Both are OOM-path
  hygiene only.

## GE + FS + O

### GE-1. The cache budget makes a second volume impossible

`cachemb()` grants `mb = budget - used` to each caller and then does
`used += mb` (`kern.c:896-901`). The first volume therefore takes the whole
budget; any later volume computes `0 < Cachemin` and is refused
(`kern.c:944-948`).

This makes `Maxvols = 4` and the `vols` list in `devgefs.c:40-54`
unreachable and prevents any two-volume test. The error message "set
gefscache=" does not help: no setting of `gefscache=` leaves a share for a
second volume under this allocator. `docs/ge-fs-o-impl.md:85` lists
"dividing the budget more evenly" as future work, but it is a prerequisite
for the second-volume entry point the same document describes as the next
step. The share is also never returned when a volume stops.

### GE-2. The user-id constants are still global

`noneid`, `nogroupid`, and `admid` remain globals (`kern.c:29-31`), and
every `loadusers()` overwrites them from its own volume's `/adm/users`
(`user.c:234-238`). `fsaccess`, `dir2statbuf`, and `fsattach` use those
globals alongside the per-volume user table (`fs.c:1132-1143`,
`pack.c:142-146`). Loading the second volume's users therefore changes how
the first volume interprets `none`/`adm`/`nogroup`, and `parseusers` uses
the previous volume's ids while parsing the next one. These belong in the
`Gefs` instance.

### GE-3. Start-up error paths

If `gefsserve` fails after `cachemb()` (for example in `newgfd` or
`loadfs`), the cache share and the allocated `Gefs` leak. `nvol` is
incremented before the cache check, so a refused attempt also consumes an
instance number. Minor, but it will make instance names and budgets
confusing once multi-volume starts to work.

## What looks correct

- The pin/K logic matches `docs/v7-upgrade.md` 4.2: the prospective user
  part is applied before the floor is computed, an already-pruned version
  is not resurrected, and a normal commit preserves the pin. `ktest fsobj`
  exercises retention and pin removal.
- Publication is a single committed `c` record; the epoch catalog, the new
  header, and the migrated records are written in the same transaction, and
  restore skips `OID_UPGRADE_META` (`p9image.c:2015`).
- The GE context propagation is mostly careful. `Limbo` is the base of the
  volume-owned objects, `unpackarena`/`unpacktree` preserve the volume, and
  the constructors (`getmount`, `getdent`, `newconn`, `dupfid`, `getdl`,
  `opentree`, `btnewscan`, `gettx`) set it. File descriptors, the console,
  halt state, sync/sweep processes, scans, and the cache are per volume.
- The test scripts were updated for the new `gefsN:` boot line
  (`gefs[0-9]*: ... read-write`).

## Test coverage gaps

- The OID of a method before and after an upgrade of its changed class.
- An upgrade from a process whose `__main__` has extra globals, including
  one that is not persistable.
- A redefined function/class, a module-level alias to a function, a changed
  base class, and a decorated module-level class.
- A real two-volume run (needs the cache fix first), including
  `none`/`adm` interpretation on both volumes.
- A caught `space.open(version=...)` failure followed by a V5/V6 historical
  open in the same process (epochs state).
